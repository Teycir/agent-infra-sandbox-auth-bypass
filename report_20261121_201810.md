## 1. Executive Summary

### 1.1 Background
Assessment of the AIO Sandbox container (`agent-infra/sandbox` v1.11.0) as deployed for agent workloads. The deployment under test had authentication **enabled** (`SANDBOX_API_KEY=testkey123`), which is the documented way to protect the sandbox. Objective: determine whether the API key gate can be bypassed and whether bypass yields meaningful access (file read, code execution).

### 1.2 Overall Posture
One systemic, critical flaw. Authentication is enforced **only** in the nginx front end via a `map "$request_method:$request_uri"` rule. Because `$request_uri` includes the query string, any `GET` request whose URL ends in a static-asset extension — trivially `?x=.json` — is routed to `@proxy_without_auth`, skipping the `auth_request` subrequest. The Rust backend (`aiod`) does not re-enforce the key on the shell/terminal routes. Result: unauthenticated arbitrary file read, unauthenticated shell session creation, and unauthenticated command execution over the terminal WebSocket, escalating to `root` via passwordless `sudo`.

This is not a scanner artifact or a theoretical path: the full chain was executed end-to-end, the extracted `/etc/passwd` hash matches the container byte-for-byte, and command output (`uid=1000(gem)`, then `uid=0(root)`) was captured and exfiltrated to a controlled listener.

**Overall risk: Critical (CVSS 3.1 9.8).** A remote, unauthenticated attacker obtains code execution in the sandbox as `gem`, then `root`, and can read/write every file the container can reach, including mounted workspaces and injected secrets.

### 1.4 Recommendation Summary
1. **RT-01 (immediate):** Match on the normalized path (`$uri`), not `$request_uri`, and never exempt API routes from auth based on a filename suffix. Enforce the API key in `aiod` as well, not only at the gateway.
2. Remove or harden the unauthenticated `terminal-url` → `/v1/shell/ws` flow; require auth on the WebSocket upgrade.
3. Defense-in-depth: bind to `127.0.0.1` by default, run as non-root without passwordless sudo, drop capabilities, read-only rootfs, no host mounts unless required.
4. Add regression tests asserting `GET /v1/file/download?path=/etc/passwd&x=.json` returns 401.

## 4. Findings Detail

### RT-01 — Authentication Bypass in nginx Static-Asset Route Matching Allows Unauthenticated RCE

- **Severity:** Critical
- **CVSS 3.1:** 9.8 — `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H` — https://www.first.org/cvss/calculator/3.1#CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H
- **CWE:** CWE-288 (Authentication Bypass Using an Alternate Path or Channel); CWE-306 (Missing Authentication for Critical Function)
- **Affected URL/Area:** `http://<host>:8080/*` — nginx auth map in `/opt/gem/nginx-server-with-auth.conf`; backend `aiod` shell/terminal routes (`/v1/shell/terminal-url`, `/v1/shell/ws`)
- **Difficulty to exploit:** Low (single query parameter, no tooling beyond curl)
- **Authentication required:** No
- **User interaction required:** No
- **Verified at (UTC):** 2026-11-21T20:13:30Z (file read), 2026-11-21T20:15:29Z (RCE), 2026-11-21T20:18:10Z (root)

#### Issue Description

`/opt/gem/nginx-server-with-auth.conf` builds the routing decision from the **raw request URI including the query string**:

```nginx
# line 11
map "$request_method:$request_uri" $target_workflow {
    ...
    # line 19
    "~*^GET:.+\.(js|css|svg|woff|json|ico|png|jpg|jpeg|gif|webp|wasm|ttf|woff2)$" @proxy_without_auth;
    ...
}
```

`$request_uri` is the full original request line target (path **plus** `?query`). A request such as:

```
GET /v1/file/download?path=/etc/passwd&x=.json
```

has `$request_uri = /v1/file/download?path=/etc/passwd&x=.json`, which ends in `.json` and therefore matches the regex. The request is routed to `@proxy_without_auth`, where the `auth_request /_auth_handler;` directive (line 42) is not applied. The request reaches `aiod` on `127.0.0.1:8091` with no key.

`aiod` does **not** re-check `SANDBOX_API_KEY` on these routes. Consequently:
- `GET /v1/file/download?path=<any file>&x=.json` reads arbitrary files.
- `GET /v1/shell/terminal-url?x=.json` mints a live shell session and returns its `session_id`.
- The terminal WebSocket `/v1/shell/ws?session_id=<id>&x=.json` is a `GET` upgrade; it is also matched by the bypass and connects without auth. Sending `{"type":"input","data":"..."}` executes commands.

The API key is only used by `gem.sh` to *select* the auth-enabled nginx config; it is not templated into nginx (the `envsubst` list excludes it). The key's only enforcement point is the nginx `auth_request` subrequest, which the suffix rule skips.

#### Attack Scenario

An attacker who can reach the sandbox HTTP port (default deployment publishes `8080`; `run.sh` warns when the listener is not localhost) needs no credentials. They:

1. Send one `GET` with `?x=.json` and read `/etc/passwd`, confirming the bypass.
2. Call `/v1/shell/terminal-url?x=.json` to obtain a shell session ID.
3. Open the terminal WebSocket with the same `?x=.json` suffix and run commands as `gem`.
4. Run `sudo -n id` — the image grants passwordless sudo — and become `root` inside the container.
5. Read agent workspace files, injected secrets, cloud metadata reachable from the container, and any mounted host directories; optionally use the browser/CDP service for further access.

#### Recommended Fix

1. **Match on the path only.** Replace `$request_uri` with `$uri` in the map (and in `X-Original-URI` where appropriate):
   ```nginx
   map "$request_method:$uri" $target_workflow { ... }
   ```
   `$uri` is normalized and excludes the query string, so `?x=.json` can no longer influence routing. Alternatively strip the query before matching (`set $path $request_uri; if ($path ~ "^([^?]*)") { set $path $1; }`), but `$uri` is the correct primitive.
2. **Do not exempt API prefixes by extension.** Restrict `@proxy_without_auth` to a dedicated static-asset prefix (e.g. `/static/`), not a suffix regex applied to every route.
3. **Enforce auth in `aiod`.** Validate `SANDBOX_API_KEY` per request in the backend for `/v1/shell/*`, `/v1/file/*`, `/v1/jupyter/*`, `/v1/browser/*`, and the WebSocket upgrade. Gateway-only auth is a single point of failure.
4. **Harden the terminal flow.** Require auth to mint a terminal session and to upgrade `/v1/shell/ws`; bind session IDs to the authenticated principal.
5. **Defense-in-depth.** Default `PUBLIC_LISTEN_IPV4=127.0.0.1`; run as non-root without passwordless sudo; drop capabilities; read-only rootfs; no host mounts by default; network egress policy.
6. **Regression test.** Assert `GET /v1/file/download?path=/etc/passwd&x=.json` and `GET /v1/shell/terminal-url?x=.json` return `401` when a key is configured.

### 5.3 Falsified / refuted items

- **Not a no-auth misconfiguration.** The baseline request returned `401`; the bypass only works because of the suffix match on the raw request URI. The deployment had `SANDBOX_API_KEY` set.
- **`/proc/self/environ` read returned 0 bytes** via `/v1/file/download`; no key material was extracted that way. Not needed — command execution was obtained directly.
- **POST-based API routes are not bypassable by this exact vector.** The map key begins with `GET:`, so `POST /v1/shell/exec` still requires auth. The RCE path used the GET-only `terminal-url` + WebSocket upgrade, which is sufficient.
- **`x-aio-proxy-port` header routing (candidate #2) was not exercised** in this run; it remains an unverified secondary hypothesis and is not claimed as a finding.
